## 二、设计规划要求（基于 v0.2-review-fixed）

### 2.1 核心功能模块

**第一阶段（P0 + P1）：**

| 功能模块 | 设计要求 | 优先级 |
|---------|---------|-------|
| 资金计划 | 资金用途、收入稳定性、损失承受能力、月政策 | P0 |
| 交易记录 | 实际现金、成交、持仓、完整交易链 | P0 |
| 策略管理 | 策略版本、适用环境、必须/排除条件、退出规则 | P1 |
| 交易计划 | 事前计划、触发/失效、预算、风险快照 | P1 |
| 复盘系统 | 盘后复盘、完整交易复盘、周/月复盘 | P1 |
| AI 理财情景 | 资金资料 → 用途、流动性、集中度比较 | P1 |
| AI 股票研究 | 行情、公告、财务 → 理由、反证、情景 | P1 |
| AI 复盘教练 | 事前快照 + 实际事实 → 判断、执行、结果评价 | P1 |

**第二阶段（P2）：**

| 功能模块 | 设计要求 | 优先级 |
|---------|---------|-------|
| 盘中提醒 | 时效与规则合格后核对盘中条件 | P2 |
| 分钟回放 | 历史分钟数据回放 | P2 |
| 约束回测 | 保留历史样本、当时可知资料、制度约束 | P2 |
| 全市场筛选 | 基于规则的选股 | P2 |

### 2.2 关键设计原则

1. **事实、计划与结果分离**
   - 实际成交、现金、持仓变动分别保存
   - 计划版本化管理，保留不可变快照
   - 结果与过程分别评价，避免事后归因

2. **精度与核算**
   - Python 使用 Decimal，PostgreSQL 使用 NUMERIC
   - 移动加权平均成本核算
   - 已实现与浮动盈亏分开

3. **数据时效与安全**
   - 每条资料保存来源、时点、作用时间
   - 历史复盘只用当时已公开信息
   - 私人数据存储于本地 PostgreSQL，账号隔离

4. **AI 可追溯性**
   - 每份报告记录截止时间、证据快照、版本
   - 主分析与反证分步完成
   - 建议卡支持采用/拒绝/未触发/无法成交

## 四、关键差距分析

### 4.1 核心差距：交易账本与成本核算

**现状：**
- 现有项目（dailyStock、TradingAgents）主要是**分析工具**，不是**交易系统**
- 没有完整的交易账本（实际成交、持仓、成本）
- 没有成本核算引擎（移动加权平均、费用分摊）
- 没有盈亏统计和报表

**设计要求：**
- 完整的交易账本（事实、计划、结果分离）
- 精确的成本核算（Decimal、NUMERIC、精度处理）
- 已实现与浮动盈亏分开
- 现金流水与成交派生项有来源关联

**差距评估：** 高难度，需要从零构建

### 4.2 核心差距：事前计划与策略管理

**现状：**
- 现有项目有交易纪律（乖离率、均线多头），但是硬编码
- 没有策略版本管理
- 没有事前计划系统

**设计要求：**
- 策略版本化，保留不可变快照
- 事前计划（触发/失效、预算、风险快照）
- 计划确认前必须具备完整条件
- 变更追加版本、理由及生效时间

**差距评估：** 中等难度，需要设计数据模型和业务逻辑

### 4.3 核心差距：复盘与 AI 教练

**现状：**
- dailyStock 有复盘功能，但主要是数据展示
- 没有系统化的复盘流程
- 没有 AI 复盘教练

**设计要求：**
- 盘后复盘、完整交易复盘、周/月复盘
- AI 复盘教练（判断/执行/结果分别评价）
- 避免事后归因
- 策略试验跟踪

**差距评估：** 中等难度，需要设计复盘流程和 AI Prompt

### 4.4 次要差距：数据时效与安全

**现状：**
- dailyStock 有数据获取，但没有系统的时效管理
- 没有明确的来源、时点、作用时间记录

**设计要求：**
- 每条资料保存来源、时点、作用时间
- 历史复盘只用当时已公开信息
- 数据过期标记

**差距评估：** 中等难度，需要设计数据模型

## 五、实施建议

1. **复用部分：**
   - dailyStock 的 AI 分析逻辑（股票研究、新闻搜索）
   - dailyStock 的多模型配置
   - stock 目录的策略代码（作为参考）
   - 量化因子教程（作为知识库内容）

2. **新建部分：**
   - 交易账本系统（P0）
   - 成本核算引擎（P0）
   - 资金计划系统（P0）
   - 策略版本管理（P1）
   - 交易计划系统（P1）
   - 复盘系统（P1）
   - AI 复盘教练（P1）

3. **整合部分：**
   - dailyStock 的 Web 界面 → 整合到 grow 项目
   - dailyStock 的推送能力 → 可选保留
   - dailyStock 的定时任务 → 支持本地运行

### 5.2 实施顺序

**P0 内部里程碑（必须先完成）：**

1. 数据模型设计（投资账户、资金流水、实际成交、完整交易链）
2. 成本核算引擎（移动加权平均、费用分摊、精度处理）
3. 资金计划系统（资金用途、风险承受能力、月政策）
4. 交易记录系统（实际成交、持仓、现金流水）
5. 账号隔离（租户隔离、授权、数据隔离）
6. 验收案例（手算例、部分卖出、费用、精度）

**P1 完整首版：**

7. 策略版本管理
8. 交易计划系统
9. 复盘系统（盘后、完整交易、周/月）
10. AI 理财情景
11. AI 股票研究（复用 dailyStock）
12. AI 复盘教练
13. CSV 导入
14. 审计更正

**P2 按能力扩展：**

15. 盘中提醒
16. 分钟回放
17. 约束回测
18. 全市场筛选

### 5.3 技术决策建议

1. **后端架构：**
   - 继续使用 FastAPI + PostgreSQL
   - 新代码放在 `知行成长/server/investments/`
   - 复用现有 `app.py` 注册路由

2. **前端架构：**
   - 使用现有静态入口与子视图
   - 图表库需要先验证（K线、体积、渲染安全）
   - 不无条件新增 pandas、TA-Lib 等依赖

3. **AI 集成：**
   - 复用现有 AI 配置（浏览器配置、账号身份）
   - 新增投资任务类型
   - 主分析与反证可使用同一模型分步完成

4. **数据源：**
   - Tushare 作为盘后候选（需核验权限）
   - AKShare 作为候选适配器
   - 公告优先交易所、巨潮、基金管理人原文

5. **精度与核算：**
   - Python 使用 Decimal，PostgreSQL 使用 NUMERIC
   - API 金额、价格、数量以十进制字符串传输
   - JavaScript 不用二进制浮点累计资金

### 5.4 风险与注意事项

1. **数据权限风险：**
   - Tushare 权限未核验，不能假设已有全部权限
   - 历史分钟、ETF分钟、实时能力需分别核验
   - 没有权限时相关入口关闭

2. **精度风险：**
   - ETF、场外基金精度处理复杂
   - 前后复权与未复权口径需分别标注
   - 费用、成本、估值缺失时明确显示

3. **AI 风险：**
   - AI 可能事后归因，需要设计反证检查
   - AI 生成的数字必须标为假设
   - 建议不能直接改成交或转移资金

4. **合规风险：**
   - 不提供投资建议，只做研究、计算、记录
   - 模型没有下单或转账工具
   - 私人数据不进入 GitHub 仓库

## 六、总结

### 6.1 现状评估

**已有基础：**
- dailyStock 项目提供了完整的 AI 股票分析能力
- TradingAgents 提供了多智能体协作框架
- stock 目录有丰富的策略代码和教程
- 用户对投资分析有深入理解

**核心缺失：**
- 没有交易账本系统（事实、计划、结果分离）
- 没有成本核算引擎（精度、费用、盈亏统计）
- 没有事前计划和策略管理
- 没有系统化的复盘流程

### 6.2 实施建议

**推荐路径：**
1. 先完成 P0（交易账本、成本核算、资金计划）
2. 再完成 P1（策略管理、交易计划、复盘、AI 教练）
3. 最后扩展 P2（盘中提醒、分钟回放、回测、全市场筛选）

**复用策略：**
- 复用 dailyStock 的 AI 分析逻辑和多模型配置
- 复用 stock 目录的策略代码作为参考
- 不直接搬入数据库、凭证、定时脚本或交易执行逻辑

**关键原则：**
- 事实、计划与结果分离
- 精度优先（Decimal、NUMERIC）
- 避免事后归因
- 数据时效与安全
- AI 可追溯性

### 6.3 下一步行动

1. **确认供应商权限：** 核验 Tushare 实际权限、限额、许可
2. **设计数据模型：** 投资账户、资金流水、实际成交、完整交易链
3. **实现成本核算引擎：** 移动加权平均、费用分摊、精度处理
4. **实现 P0 功能：** 资金计划、交易记录、持仓核对
