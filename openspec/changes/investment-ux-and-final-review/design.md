## Decisions

### 决策 1：浏览器测试策略

**选择：** 手动测试 + 自动化脚本验证关键路径

**理由：**
- 手动测试可以发现 UI/UX 问题和布局问题
- 自动化脚本可以验证核心功能逻辑
- 不需要引入 Selenium/Playwright 等重量级工具
- 已有 P0 自动化测试脚本可复用

**替代方案：**
- 使用 Playwright/Selenium 完全自动化：成本高，维护复杂
- 仅手动测试：无法保证回归测试覆盖

### 决策 2：移动端布局方案

**选择：** 响应式设计 + 移动端优先

**理由：**
- 复用现有 CSS 框架（如果有）或自定义响应式 CSS
- 使用 flexbox/grid 实现自适应布局
- 表单和按钮在移动端友好（足够大、间距合理）
- 表格在移动端使用卡片式布局

**替代方案：**
- 独立的移动端页面：维护成本高
- 使用 React Native 等框架：学习成本高，与现有架构不符

### 决策 3：全市场筛选引擎设计

**选择：** 基于规则的筛选引擎 + 可扩展的条件系统

**理由：**
- 使用 Python 实现筛选逻辑，支持 AND/OR 组合
- 筛选条件定义为可配置的规则（如 `price_change_7d > 10`）
- 筛选结果分页展示，支持排序
- 筛选方案保存为 JSON，可复用

**数据模型：**
```python
class ScreenerCondition:
    field: str  # 如 'price_change_7d', 'volume_ratio', 'turnover_rate'
    operator: str  # '>', '<', '>=', '<=', '==', 'between'
    value: Decimal | tuple[Decimal, Decimal]

class ScreenerPreset:
    name: str
    conditions: list[ScreenerCondition]
    logic: str  # 'AND' or 'OR'
```

**替代方案：**
- 使用 SQL 直接查询：灵活性差，难以扩展
- 使用第三方筛选库：增加依赖，学习成本

### 决策 4：盘中价格提醒机制

**选择：** 定时轮询 + 浏览器通知

**理由：**
- 前端定时（如每 5 分钟）轮询后端 API 获取最新价格
- 后端从数据源获取最新价格（Tushare/AKShare）
- 前端使用 `Notification API` 发送浏览器通知
- 提醒规则保存为 JSON，支持多个条件

**数据模型：**
```python
class PriceAlert:
    instrument_id: str
    condition: str  # 'price_above', 'price_below', 'change_pct_above'
    threshold: Decimal
    enabled: bool
    last_triggered_at: datetime | None
```

**替代方案：**
- WebSocket 实时推送：实现复杂，需要额外基础设施
- 邮件/短信通知：成本高，延迟大
- 服务端后台任务：需要定时任务框架，复杂度高

### 决策 5：分钟回放实现方案

**选择：** 按需加载 + 前端渲染

**理由：**
- 分钟数据存储在数据库，按需查询
- 前端使用图表库（如 ECharts）渲染 K 线图
- 支持播放控制（播放、暂停、快进、快退）
- 技术指标在前端计算并叠加显示

**数据模型：**
```python
class MinuteData:
    ts_code: str
    trade_date: date
    minute: int  # 0-240 (4 hours of trading)
    open: Decimal
    high: Decimal
    low: Decimal
    close: Decimal
    volume: Decimal
```

**替代方案：**
- 预计算所有分钟数据：存储成本高
- 使用第三方回放服务：依赖外部服务
- 后端渲染图表：前端交互性差

### 决策 6：策略回测引擎设计

**选择：** 事件驱动回测引擎 + 约束检查

**理由：**
- 按时间顺序处理历史数据，模拟交易执行
- 支持交易约束检查（T+1、涨跌停、停牌等）
- 支持费用模拟（佣金、印花税、滑点）
- 生成回测报告（收益率、最大回撤、夏普比率等）

**回测流程：**
1. 加载历史数据（日线或分钟线）
2. 按时间顺序遍历每个时间点
3. 执行策略逻辑，生成买卖信号
4. 检查约束条件（T+1、涨跌停等）
5. 模拟成交，更新持仓和现金
6. 计算绩效指标

**替代方案：**
- 使用第三方回测框架（如 Backtrader）：学习成本高，灵活性差
- 向量化回测：难以处理复杂约束
- 蒙特卡洛模拟：不适用于确定性策略

### 决策 7：代码审查流程

**选择：** 分层审查 + 分批次提交

**理由：**
- 先审查核心逻辑（成本核算、数据模型）
- 再审查 API 设计和安全性
- 最后审查前端交互和 UI
- 按功能模块分批次提交，每个 commit 有清晰的 message
- 生成 PR 描述，说明变更内容和测试情况

**提交顺序：**
1. 用户体验优化（测试、布局、错误提示）
2. 全市场筛选功能
3. 价格提醒功能
4. 分钟回放功能
5. 策略回测功能
6. 文档更新

**替代方案：**
- 一次性提交所有变更：难以 review，风险高
- 使用自动化代码审查工具：无法发现业务逻辑问题

## Risks / Trade-offs

### 风险 1：移动端兼容性问题

**风险描述：** 不同浏览器和设备的兼容性问题可能导致布局错乱或功能异常

**缓解措施：**
- 优先测试主流浏览器（Chrome、Safari）
- 使用 CSS 前缀和 polyfill 保证兼容性
- 提供降级方案（如表格在移动端显示为卡片）

### 风险 2：数据源权限不足

**风险描述：** Tushare 权限可能不支持分钟数据或高级接口

**缓解措施：**
- 优先使用 AKShare 作为备选
- 如果权限不足，限制 P2 功能的使用范围（如仅支持日线回测）
- 明确告知用户功能限制

### 风险 3：回测性能问题

**风险描述：** 大量历史数据回测可能导致性能问题

**缓解措施：**
- 限制回测时间范围（如最多 5 年）
- 使用异步任务处理回测请求
- 提供回测进度反馈

### 风险 4：价格提醒延迟

**风险描述：** 定时轮询可能导致提醒延迟（最多 5 分钟）

**缓解措施：**
- 明确告知用户提醒可能有延迟
- 提供可配置的轮询间隔
- 未来可升级为 WebSocket 实时推送

### 风险 5：代码审查遗漏问题

**风险描述：** 人工审查可能遗漏安全漏洞或性能问题

**缓解措施：**
- 使用自动化工具辅助审查（如 linter、security scanner）
- 重点审查核心逻辑（成本核算、数据隔离）
- 进行端到端测试验证

### Trade-off 1：功能完整性 vs 交付时间

**权衡：** 完整实现所有 P2 功能需要 2-3 周，可能影响交付时间

**决策：** 优先实现核心功能（全市场筛选、价格提醒），分钟回放和回测可以简化实现或延后

### Trade-off 2：性能 vs 功能丰富度

**权衡：** 复杂的功能（如实时行情、大规模回测）可能影响性能

**决策：** 优先保证核心功能的性能和稳定性，高级功能作为可选增强
