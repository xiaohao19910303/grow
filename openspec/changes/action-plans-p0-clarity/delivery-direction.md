# 交付方向：网页优先、独立部署、预留连接能力

2026-10-22，根据用户本轮指示调整开发顺序：先完善网页版本，App 与 Zook 后端后续完善；设计兼顾独立部署与未来连接部署。

## 当前优先级

1. 优先完善 Grow 网页的创建、安排、执行、来源确认、记录、复盘和失败恢复；网页功能与验收以 Grow 自身后端和数据库为基础，不要求先上线 Zook 或完成原生端。
2. C4 原生消费者与 C5 真实双端验收暂缓。原生仓库本轮仅检查，未修改代码；既有 C0–C3 实现和验收证据保留，不因此启用连接写入。
3. 新的网页缺口先按实际页面、业务规则和可复现用例确定，再建立实施任务；本次方向调整不增加 P1/P2，也不宣称已有独立部署全流程通过验收。

## 两种部署形态

| 形态 | 组成与业务归属 | 依赖与边界 |
| --- | --- | --- |
| 独立网页部署（优先交付） | Grow 网页 + Grow 服务端 + PostgreSQL，行动由 Grow 写入 | 不依赖 App、Zook、配对或共享桥接密钥；“独立”指可脱离 Zook 运行，不代表只部署静态前端即可提供完整功能 |
| 后续连接部署 | Grow 网页/来源服务，与 Zook 共享行动后端及 App 对接 | 账号经明确接管后才可切换行动写入归属；来源正文和私人反馈仍由 Grow 管理。需合同、消费者和迁移验收后另行放行 |

当前代码已有默认 local 的独立行动路径以及 pending/active 屏障。独立部署的安装、配置、数据库初始化、启动、备份恢复和浏览器全流程仍应作为独立验收项执行；此前隔离功能回归不等于完整部署验收。

## 后续开发约束

- 网页通过明确的服务端 API 获取业务状态、提交命令和核对回执；完成规则、版本检查、来源证据、幂等与事实写入由服务端负责，不写成只能由浏览器页面驱动的规则。未来 App 可以实现相同语义，界面不必照搬网页。
- 网页当前使用 Grow 私有 API；对接 Zook 时遵守 Zook 唯一公共 OpenAPI 与已验证提交。不能要求每个网页改动都先实现 Zook，也不另建一份竞争的公共合同源。
- 传输/鉴权与页面状态分离，使用现有桥接边界承接后续适配；需要新增适配时按实际差异实施，不提前建设通用插件、双后端框架或新微服务。
- 同一账号的行动始终只有一个写入方。独立模式写 Grow；连接模式须经过接管，pending 失败保持屏障。Zook 不可达时不能静默回退本地双写。
- 维持明确的 ID、nullable 字段、模式、状态、revision、事实和请求 key 语义；新增接口避免依赖浏览器存储、固定域名或设备本地时钟才能正确执行。草稿与待核对请求继续按账号隔离。
- 跨端来源完成只能依赖经过验证的来源确认事件；App 的已读位、计时到点或网页滚动不能代替完成证明。未实现的平台能力明确展示限制。
- 新能力逐项验收。网页验收、独立部署验收、连接合同验收、原生/设备验收分开记录；App 未完成不应阻塞已独立验收的网页版本，网页通过也不能用来放行连接写入。

## 当前状态记录

Grow 本地功能和 C0–C3 的已通过证据继续有效，最新 C3 结果见 [切换验收报告](handoff-cutover-verification.md)。OpenSpec 7.3 保持未完成，表示未来连接交付仍有 C4/C5 等缺口；它不是独立网页可用性的统一阻塞项。下一轮工作应从网页实际缺口与独立部署验收进入，不自动继续 C4。
